Les couches :
1. Le système : Windows envoie WM_KEYDOWN (ou WM_SYSKEYDOWN pour les combinaisons avec Alt), avec le code virtuel dans WPARAM et le scancode dans LPARAM. Lien : un commentaire — NkKeycodeMap.h rappelle « Dans le backend Windows : traitement d'un message WM_KEYDOWN » et reprend le test des quatre messages ; l'énoncé le donne aussi. Rien dans les en-têtes du kit ne cite littéralement WM_KEYDOWN comme code exécuté : le catalogue de touches (NkKeycodeMap.h) ne fait que la correspondance VK → NkKey, et son commentaire est ce qui nomme le message. C'est le seul maillon tenu par un commentaire.
2. Le filtre et la traduction : NkEventSystem (include/NKWindow/Core/NkEventSystem.h, implémenté dans Private/Win32/NkWin32EventSystem.cpp). Lien : du code — la boucle de pompe dépile les messages de la file du système et les envoie à la procédure de fenêtre par DispatchMessageW ; c'est un appel de code, pas une description.
3. La procédure de fenêtre : NkWin32WndProc, déclarée dans include/NKWindow/Platform/Win32/NkWin32EventSystem.h et enregistrée dans WNDCLASSEXW par NkWin32Window (« data only, no methods », include/NKWindow/Platform/Win32/NkWin32Window.h — les fonctions d'accès seulement, le corps vit dans le .cpp). Lien : du code — la déclaration nomme la fonction, l'en-tête de NkWin32Window annonce son enregistrement, et l'en-tête de NkWin32EventSystem ne contient que cette déclaration, ce qui montre que le corps est ailleurs.
4. La création de l'événement typé : le même fichier, dans le corps de NkWin32_ProcessMessage. Le code y lit le scancode dans les bits 16-23 de LPARAM, l'indicateur étendu au bit 24, le bit de répétition au bit 30, convertit par NkKeycodeMap (NkScancode → NkKey) et fabrique un NkKeyPressEvent (ou NkKeyRepeatEvent si le bit de répétition est posé). Lien : du code — les classes d'événement sont celles de include/NKEvent/NkKeyboardEvent.h, et la conversion dans NKEvent/NkKeycodeMap.h.
5. La mise en file et le pompage : NkEventSystem::PollEvent (include/NKWindow/Core/NkEventSystem.h). L'événement fabriqué est déposé dans la file du système, puis la coquille le dépile : NkCanvasApp::PumpEvents, dans NKCanvas/App/NkCanvasApp.h, appelle NkEvents().PollEvent() en boucle. Lien : du code — la signature PollEvent est déclarée dans l'en-tête, et le cycle « pompe puis événement typé » du fichier de coquille le confirme.
6. L'aiguillage vers ma méthode : NkCanvasApp::DispatchTyped, déclarée dans le même NkCanvasApp.h, teste event.As<NkKeyPressEvent>() et appelle OnKeyPress. Lien : du code pour la déclaration (DispatchTyped est privée, l'en-tête dit seulement qu'elle aiguille les virtuelles typées), et du commentaire pour le détail du test As<> — le chemin complet, de As<> à OnKeyPress, je ne l'ai lu nulle part en entier, je l'ai déduit du nom et du commentaire de l'en-tête.
7. L'arrivée : MaClasse::OnKeyPress, la virtuelle de NkCanvasApp que mon application redéfinit. Lien : du code — sa signature est déclarée dans NkCanvasApp.h, sous « A remplir par l'application ».

Où je me suis arrêté : à NkWin32_ProcessMessage et à NkCanvasApp::DispatchTyped. Pour les deux, le corps qui décide vraiment — les seize cas du switch de la procédure de fenêtre, et le test As<NkKeyPressEvent>() de l'aiguillage — n'est pas dans un en-tête sous include/ : il est dans un .cpp compilé, dont j'ai lu quelques passages hors du kit. Et la toute première couche — la procédure que Windows appelle, et l'endroit exact où le message entre dans la file — n'est visible que dans un commentaire : aucun en-tête du kit ne porte de ligne exécutable sur WM_KEYDOWN, seulement le catalogue de touches et le rappel de NkKeycodeMap.h. C'est là que je me suis arrêté volontairement : ce qui manque n'est pas dans les en-têtes du kit, et je n'ai pas compilé un programme avec un point d'arrêt pour le prouver par la pile.

Combien : sept couches, et j'en ai vu travailler trois — la création de l'événement typé (NkWin32_ProcessMessage), la mise en file et le dépilement (NkEventSystem::PollEvent appelé par NkCanvasApp::PumpEvents), et l'aiguillage (DispatchTyped). Les quatre autres, je les ai vues seulement nommées : le message du système par un commentaire, la traduction par un appel que je n'ai pas lu en entier, la procédure de fenêtre par sa déclaration, et OnKeyPress par sa signature dans la coquille.
