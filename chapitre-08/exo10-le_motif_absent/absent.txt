L'endroit : le choix du dorsal graphique est écrit deux fois dans les en-têtes du kit, et une troisième fois dispersé dans les valeurs de l'énumération.
- NKCanvas/Factory/NkContextFactory.h — une fabrique de contexte par API, avec un switch sur NkGraphicsApi (Create, puis IsApiSupported) : c'est le premier cas.
- NKCanvas/Renderer/Core/NkRenderer2DFactory.h:36 — static NkIRenderer2D *Create(NkIGraphicsContext *ctx); et IsApiSupported, qui refont le MÊME choix, sur la MÊME énumération, pour le rendu 2D : c'est le deuxième cas. Et il a déjà divergé : la fabrique de contexte connaît Metal, la fabrique de rendu 2D répond false pour Metal (NkRenderer2DFactory.cpp) alors que NkMetalRenderer2D.h présente son rendu comme livré.
- NKCanvas/App/NkCanvasApp.h — le choix apparaît une troisième fois, dans NkCanvasApp::ResoudreBackend, qui traduit la ligne de commande, la variable d'environnement et Config().backend en une valeur de NkGraphicsApi : la sélection y est répétée en dehors des deux fabriques.
- NKCanvas/Core/NkContextDesc.h — la même énumération traverse NkContextDesc et ses fabriques MakeOpenGL, MakeVulkan, MakeDX11 : chaque backend y est encore nommé une fois.
Ce qui se répète, ligne à ligne : pour chaque API, on écrit un « cas » (identifiant + contexte à créer) dans au moins deux endroits, et un « nom » dans un troisième. Ajouter Metal a demandé de le faire dans NkContextFactory (code), dans NkMetalRenderer2D (le dorsal), et dans NkRenderer2DFactory où le cas est encore écrit « not yet implemented ». Le troisième cas qui arrive — un backend logiciel sans fenêtre, ou Metal achevé — devra se souvenir des trois endroits, et le commentaire de NkRenderer2DFactory.h qui oublie Metal montre qu'on n'y arrive déjà plus.

Le motif : une Fabrique de fabriques (Kit de fabrique / Abstract Factory), avec un Registre à la place des trois switch. Concrètement : une interface NkBackendProvider { Nom, CréerContexte(const NkContextDesc&), CréerRenderer2D(NkIGraphicsContext&), EstSupporté() }, une implémentation par backend, toutes enregistrées une fois au démarrage dans une petite table indexée par NkGraphicsApi. Les deux fabriques existantes deviennent des requêtes à cette table, ResoudreBackend n'a plus qu'à produire un identifiant, et ajouter un backend devient l'écriture d'un seul fichier plus son enregistrement — ce que le chapitre appelle « la fabrique qui fait son travail ». C'est le motif du catalogue qui règle exactement ce problème de deux choix interdépendants (contexte, rendu 2D) sur un même identifiant ; un simple « fabrique » par API, testée séparément, laisserait la divergence possible.

Le coût : quatre fichiers d'en-tête à changer (NkContextFactory.h, NkRenderer2DFactory.h, NkContextDesc.h, NkCanvasApp.h — ce dernier parce que ResoudreBackend y vit) et deux fichiers de bibliothèque (.cpp) qui contiennent les deux switch. Ce qui risque de casser : les appels directs à NkContextFactory::Create / CreateWithFallback, qui rendent aujourd'hui un pointeur de contexte nu — les passer par une table change leur signature de retour et la vie de l'objet ; la capture, qui ne marche qu'en DirectX 11, dépend d'une méthode du dorsal concret et exigerait une entrée de la table (« supports capture ») plutôt qu'un if ; enfin, le repli entre API (CreateWithFallback essaie une liste dans l'ordre) devra être conservé dans la table, sinon un échec silencieux reviendra aux backends déjà validés. Le coût est réel, et c'est pourquoi ce n'est pas le premier cas qui justifiait de le payer : c'est le troisième, celui où Metal est écrit mais n'est pas encore branché.
